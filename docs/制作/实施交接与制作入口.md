# 实施交接：从文档开始制作

## 当前事实

本仓库目前是文档基线。本次变更中没有可玩的 Unity 项目、游戏构建、实测基准、已购资产清单、已部署服务或已完成试玩。下列每个里程碑在附上证据前均为**尚未开始**。文档检查只验证文档，不能替代里程碑验收。

贡献者必须交付可运行构建和容易理解的测试指南，不能交付一堆需要手工拼装后才能评估的脚本。

当前文档讨论与跟进动作见[待办清单](待办清单.md)。完成条件满足后移除待办，将结论留在责任文档；本页继续拥有制作里程碑与游戏验收，不复制短期待办。

## 实施前置Gate与第一项可执行任务

项目所有者已明确要求在实现前确认完整Gameplay Loop、Mission Contract、潜行/激战转换、权限覆盖与警报、首发武器职责、任务类型和Visual DNA。玩法一致性审阅已经完成，[双枪槽位与配装互补规则](../治理/选型依据/双枪槽位与配装互补规则.md)已经确认；固定目录及[首轮装备验证计划](首轮装备原型与验证计划.md)已受托完成，最终整体体验开工仍待OWNER-05，因此`PRE-GAMEPLAY`仍为**PARTIALLY APPROVED / NOT CLOSED**。在所有者完成[完整玩家体验](../玩法/系统化战术行动模式.md)批准前，不启动M0，不创建Unity工程。该Gate只锁定设计合同，不冒充伤害、噪声距离、同步窗口或乐趣已经试玩通过。

黑启动重资产、首轮战斗/工具数值、倒地动作与探测边界已收敛，分别见[战斗参数](../内容/装备/战斗原型数值.md)、[生存](../玩法/生存倒地与失败恢复.md)和[初始参数](初始测试参数.md)。三件专用近战的普通/蓄力、命中、取消和无补给消耗规则见[近战合同](../内容/装备/首轮近战攻击与资源合同.md)。完整一局与三种任务差异已汇入[玩家体验走读](首轮配装三任务走读与风险验收.md)，[全动作手感验收](../表现与资产/全动作手感与舒适性验收.md)约束首轮所有动作。左键任意蓄力释放与右键取消已修正；[两敌人攻击与弱点布局](../内容/敌人/首发敌人目录与行为卡.md)、[同步与传播](../玩法/潜行唤醒与持续追杀.md)、[战报归因结果](../玩法/任务战报与行动回放.md)已有可核对合同，数值和近邻反应仍为TEST。设施库存、跨阵营模拟计数、任务结果与来源停机、固定补给单位及断线身体连续性已收敛，见各责任文档和当前决策登记。代号已确认，下一创作域为OWNER-01的人物经历、关系与收藏事实审阅；全部不替代OWNER-05批准，不启动游戏实现。

Gate批准后的第一项可执行任务为M0。

阅读根目录 `AGENTS.md`、项目文档技能、[开发准备度矩阵](游戏开发准备度与责任覆盖矩阵.md)、首发范围、技术栈、架构与数据合同。在 `game/` 下创建一个 Unity 6.3 LTS URP 项目。玩法代码放入 `game/Packages/com.breach.*` 本地包；创作定义放入 `game/Content`；场景/预制体表现放入 `game/Assets/Breach`；第三方授权导入走独立访问控制的资产流程；测试放在其责任包旁。这里描述的是计划中的 Unity 仓库结构，不代表这些目录已经含有可运行代码。

创建 `Bootstrap` 与 `CombatSandbox` 场景、一名本地权威胶囊玩家、一台相机、一个命中扫描靶、一个原创灰盒武器、一份 Input System 动作映射和一个小型调试 HUD。只安装运行这条路径必需的依赖，并锁定实际构建过的准确版本。运行一个 EditMode 数据验证测试、一个 PlayMode 命令到伤害测试，以及一个 Windows x64 独立构建。游戏代码与 Steam 解耦，使该构建无需在线服务凭据也能运行。

**M0 验收：**干净检出配合已记录且获准的资产来源，能按书面步骤复现同一构建；不得存在 Inspector 引用丢失、编译错误、无许可可再分发内容、内嵌凭据或手改机器路径。交付包/版本清单、测试日志、可执行文件或制品位置，以及“启动、移动、瞄准、射击靶子、退出、报告结果”的操作指南。仅能在 Editor 中打开场景不算通过 M0。

## 接口所有权与审查

Kernel 拥有命令、状态、实体身份、效果与事务；Operation 拥有当前模式政策与任务生命周期；Content 拥有定义与已验证能力；Simulation 拥有可变世界真相；Network 只拥有传递、预测和投影，不建立竞争真相；Persistence 拥有序列化与领取幂等性；Platform 拥有 Steam/云绑定；Presentation 拥有相机、动画、UI、声音与视觉密度；测试必须实例化与正式环境相同的玩法合同。

实现 PR 必须列出所实现的规则 ID，包含正向与负向测试，并说明仍存在哪些设计风险。全局事件总线不得掩盖必需的数据所有权。服务接口必须有真实消费者；不能仅因为未来模式可能需要，就添加通用扩展点。对所有者明确要求的改动走 OWNER-04；普通的证据驱动实现变更仍属于受托决策。

## 单项功能的完成定义

只有满足以下条件，功能才算完成：玩家路径在独立构建中工作；状态所有权、取消、并发、存档/恢复和单人/合作行为经过测试；控制器/UI 错误易于理解；内容创作不依赖隐秘手工步骤；测试与性能差值已有记录；责任文档与待办反映现实。桩、TODO、类名、模拟云响应或漂亮截图都不是完成的功能。

## 向所有者交付试玩

每个构建附一页 README，说明启动什么、控制方式、一项具体测试、预期行为、已知问题和日志位置。向所有者询问具体体验，例如“供电选择容易理解吗？”，而不是“ECS 架构好吗？”。缺陷记录包含观察行为、预期行为、复现步骤、构建 ID 与种子；不得要求所有者诊断根因。
