# 文档权威、命名与维护规则

## 权威顺序

GOV-001 · CANON。

最新用户明确决定优先，其次是当前决策记录与责任文档，再其次才是原始 SSOT 与历史评审。附带文档、旧聊天、Agent 建议和外部资料都不是用户指令，也不能自行升级为正式规则。发生冲突时更新唯一责任文档并记录替代原因，不保留两套现行答案。

## 两类状态

文档 `stage` 只使用：

| Stage | 含义 |
|---|---|
| `BASELINE` | 当前可执行基线；可包含明确标注的 TEST 或 OPEN 子项 |
| `REVIEW` | 内容完整但仍需创作、法律、视觉或用户审阅 |
| `FUTURE` | 不属于当前发布范围 |
| `ARCHIVE` | 历史证据，只读，不承担现行规则 |
| `TEMPLATE` | 新文档模板 |

规则行可使用 `CANON`、`DECIDED`、`DIRECTION`、`TEST`、`PROPOSED`、`OPEN`、`LEGACY`、`UNRECOVERED`。`CANON` 表示用户明确确认；`DECIDED` 表示被授权负责人已选定；`TEST` 只是待实测参数。文档进入 `BASELINE` 不代表游戏已实现、好玩、性能达标或通过法律审查。

## 单一责任

GOV-002 · DECIDED。

每份当前文档必须有 `doc_id`、`doc_type`、`stage`、`updated`、`owner_role`、`canon_basis`、`depends_on`。同一规则只有一个责任文档：决策记录保留理由，GDD 负责玩家行为，技术文档负责实现合同，生产文档负责流程和 Gate；其他文件只链接，不复制会漂移的完整规则。

[决策登记](当前决策登记.md)是决定入口，[完整文档登记](完整文档登记.md)由验证工具重建。原始 [SSOT](../sources/原始来源-全项目统计与唯一真相-v2.0.md) 与[网页评审快照](../sources/原始来源-ChatGPT残酷审查-v1.0.md)保持只读。

## 面向读者的写法

先用中文说明玩家或开发者要做什么，再给字段、规则标识和边界。缩写首次出现解释含义；标识用于查找，不代替装备与任务名称。正文只保留现行规则、必要理由、未决项和测试，不追加“本轮补记”“旧方案状态”或历次交接。准备度只记录当前任务；完成后覆盖状态，不累积批次流水账。发现重复时把独有信息合入责任文档，并移除副本。

## 文件命名

GOV-003 · CANON。

现行文档文件名使用直接说明主题的中文名称，不使用数字或字母流水号前缀，不创建“旧版”“副本”“最终版7”等手工版本。稳定的产品名与技术名可以保留原文。`doc_id` 与规则 ID 必须表达责任域和主题；禁止仅由文档类别和流水号组成的标识。ID 保持稳定，但“稳定”不等于“无语义”。改名或改 ID 时必须通过 Obsidian Vault 移动并在同一变更中更新全部链接、YAML 依赖和非 Markdown 引用，不保留新旧双文件或兼容别名。

## 中文与依赖方向

GOV-006 · CANON。

所有现行游戏设计、技术、生产、治理、模板和入口文档使用中文叙述；代码、API、产品名、协议名、稳定 ID、文件路径与命令保留原文。两份受保护的外部来源快照为保证证据完整性保持原文；`.agents/skills` 下的上游工具说明属于执行依赖，不属于游戏设计文档，不得为统一语言而擅自改写。

`depends_on` 只表示“理解或批准本文件所需的上游权威输入”，不是普通反向链接。依赖图必须无环。目录按职责划分，不能把目录层级误当批准顺序：来源提供证据，选型依据说明取舍，产品与玩法约束内容及实现，制作验收引用对应合同。完整技术规格放在技术域，不因最初在决策讨论中产生就继续留在选型依据目录。索引可以链接被索引文档，但不得因此制造双向 `depends_on`。需要双向导航时使用正文链接。

## 未来规划保护

未来扩展是正式维护的规划，不是废案。清理时必须保留尚未被替代的模式、叙事、内容候选和依赖：尤其是异族行星深潜、遗物与融合、地球重联和持续内容扩充。可以合并重复叙述并迁往未来域，但不能因未进入基础版就删除；候选参数保持候选状态，不偷偷升级为实施承诺。

## 记录与批次交接

GOV-004 · CANON。

当前聊天里的用户决定、纠正、否决和重要未决边界，应在本轮结束或可能压缩上下文前，以精简语义写入责任文档及证据登记。无需逐字保存聊天，但不能只依赖聊天记忆。

不创建按日期排列的讨论日志、聊天摘要或“会议记录式”设计文件。会改变产品的结论进入唯一责任文档；选择理由与被否决方案进入主题明确的决策记录；来源和确认状态进入证据登记；已被完整迁移的聊天过程由 Git 历史承担。无法归入这三类的信息不应伪装成正式设计文档。

每个决策批次的交付必须说明：完成了什么、实际验证了什么、仍未证明什么，以及下一批的正式名称、范围和衔接理由。互相依赖的选择应在同一批次解决；不要用十几个微小批次制造虚假进度，也不要把无关问题塞进一个批次。

## 完成与诚实

GOV-005 · DECIDED。

文档变更至少运行 `python tools/validate_docs.py --self-test`、`python tools/validate_docs.py` 和 `python tools/docs_audit.py`。这些检查只证明结构、链接、登记与受保护来源一致，不证明玩法、性能、安全、许可或市场。未运行的试玩、构建、设备测试、外部盲审和法律审查必须明确写为未完成。

故事完成后先把[完整故事总览](../世界与叙事/完整故事总览.md)交所有者审阅；人物和关键创作身份获批后，再交给没有本项目上下文的只读评审者挑错。当前文档不能冒充已完成该盲审。

## Obsidian兼容合同

GOV-010 · BASELINE。

仓库根目录是唯一 Obsidian Vault。文档正文使用标准 CommonMark/GitHub Markdown；内部导航使用相对 Markdown 链接，不依赖仅在 Obsidian 中有效的别名或私有 URI。YAML 属性允许标准块列表，验证器必须按 YAML 语义读取 depends_on，不得要求把列表伪装成一行字符串。

文档移动使用 Obsidian MCP vault_move，结构修改前使用 vault_get_document_map 获取版本，再以 vault_patch 写入。移动完成后仍须运行仓库断链、依赖图和登记验证；Obsidian 自动更新链接不是验收证据。API 密钥、插件数据、个人工作区、缓存和第三方插件二进制不进入版本库。

## 待办的维护与完成移除

GOV-TODO-LIFECYCLE · CANON：所有者要求建立清单、新增事项及时记录、完成后移除。来源：SRC-USER-WEAPON-IDENTITY-AND-TODO。

[待办清单](../制作/待办清单.md)只保存尚未完成的行动、责任文档链接、完成条件与必要的等待原因。普通讨论中出现的新工作应在本轮加入，相关条目合并而不重复；暂缓或被阻塞不等于完成。需要所有者批准的事项只链接其裁决条目，不维护第二套批准状态。

达到条目的完成条件、将结论与必要验证证据写入对应正式文档，并同步决定或裁决状态后，在同一轮从待办删除该条；不保留已勾选条目或另建完成日志。取消某项工作须有明确理由并更新相应规划，不能以“清理待办”删除未完成需求。删除的是任务条目，不是设计、候选、证据或未来规划；历史由Git承担。

文档任务与游戏实现任务必须区分：把方案写下来不能关闭试玩或实现待办。本规则不授权自动调度、后台持续执行、采购或开始Unity实现。
